# Refactoring Decisions: Cypress to Playwright

This document outlines the key architectural and technical changes made during the porting process from the original Cypress suite to Playwright.

## 1. Precise Selectors over Partial Matches
- **Change:** Replaced `[data-test*="selector"]` (Cypress `getBySelLike`) with exact matches `[data-test="selector"]` where applicable.
- **Reasoning:** Partial matches (`*=`) are more prone to "false positives". However, we discovered that for certain Material-UI components (like Bank Account inputs), partial matches are necessary because the framework appends dynamic suffixes to the `data-test` attributes. 
- **Outcome:** We used exact matches for stable identifiers and kept partial matches for decorated components, striking a balance between precision and reliability.

## 2. Externalized Test Data
- **Change:** Moved hardcoded strings (passwords, user info) from test files to `playwright-tests/test-data/`.
- **Reasoning:** Centralizing test data follows the DRY (Don't Repeat Yourself) principle. It makes maintenance easier—if a default password changes, it only needs to be updated in one place rather than across multiple test files.

## 3. Behavioral Session Verification
- **Change:** Replaced direct cookie inspection (`connect.sid`) with a page reload verification.
- **Reasoning:** In a modern web environment, especially on `localhost` with `HttpOnly` cookies, direct cookie access can be flaky. A behavioral test (logging in, reloading, and checking if still logged in) is a more reliable way to verify the user experience and the effective persistence of the session.

## 4. Seed-Agnostic User Retrieval
- **Change:** Tests dynamically fetch an available user from the database via API instead of using hardcoded usernames like `Katharina_Bernier`.
- **Reasoning:** Since the application uses random data generation (`faker`) during the seed process, hardcoded names are unreliable. Dynamic retrieval ensures that tests pass regardless of the specific strings generated by the seed task.

## 5. Granular POM Methods (Atomicity)
- **Change:** Refactored complex methods like `completeOnboarding` into smaller, atomic actions (`startOnboarding`, `fillBankAccountForm`, `submitBankAccountForm`).
- **Reasoning:** Breaking down large procedures into smaller methods increases the reusability of the Page Object. It allows for more specific testing scenarios (e.g., verifying form validation error states) without having to execute the entire onboarding flow. This follows the Single Responsibility Principle within the Page Object context.
